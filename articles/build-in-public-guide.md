2023年2月、AFFiNEのローンチ当日。私たちは少し怖いことをした——スター数がリアルタイムで増えていく様子も、必死で直していたバグも、荒れ始めたHacker Newsのスレッドも、ぜんぶ公開した。（共同創業者には「正気か」と言われた。）

2年後、AFFiNEのGitHubスターは**6万以上**に。その成長の大きな部分は、ひとつの習慣に遡る——**Build in Public(公開しながら作る)**だ。後から書く綺麗なケーススタディではなく、リアルタイムで、オープンに、だ。

この記事は、その実践ガイド。**何を・どこで・どのくらいの頻度で**共有するか、そして逆効果になる失敗まで。

---

## なぜ Build in Public は効くのか

| レバー | 積み上がるもの |
|--------|--------------|
| 数字を公開する(小さくても)| **信頼** — 具体的な数字は形容詞に勝つ |
| 成功だけでなく失敗も共有 | **信用** — 弱さを見せるほうが速く伝わる |
| 一貫した頻度 | **オーディエンス** — 投稿ごとに増える |
| 制作途中のデモ | **フィードバック** — 間違ったものを出す前に直せる |
| 公開された勢い | **社会的証明** — 購入のリスクを下げる |

ポイントは「映え」ではなく、**ディストリビューションと信頼**。見知らぬ人を、応援し、フィードバックをくれ、最初のユーザーになってくれるオーディエンスに変える。

## 何を共有するか(5つのバケツ)

1. **数字** — MRR、登録数、スター、流入。小さくてOK。具体性が信頼になる。
2. **意思決定** — なぜAではなくBを選んだか。人はあなたの判断から学ぶ。
3. **失敗** — コケたローンチ、誰も使わなかった機能。（一番うまくいかなかったProduct Huntのほうが、成功時より多くを読者に教えた。）
4. **マイルストーン** — 初の有料顧客、100スター、リデザイン。
5. **舞台裏** — 制作途中のスクショ、デバッグ中のデモ。

共有しないもの:ユーザーを危険にさらす情報、未公表のセキュリティ問題、内部対立。

## どこでやるか

ユーザーがいる場所を選び、**続けられる1つから**始める(全部やろうとしない):

- **X(Twitter)** — インディー/スタートアップ層。スレッド+短い日次更新。
- **GitHub** — 開発者向けには、良いREADMEと活発なIssuesがそのまま「公開」になる。
- **Reddit** — ニッチコミュニティ(r/SaaS等)。価値9:宣伝1。
- **自分のブログ** — SEOに効く、恒久的なホームベース。
- **Zenn / Qiita** — 日本の開発者に届けるなら。

## 強度より「頻度」

静かになった瞬間にフライホイールは止まる。英雄的な1週間より、続く習慣が勝つ。

- **ほぼ毎日**:Xで小さな更新を1つ(数字、スクショ、学び)。
- **毎週**:少し長めの投稿——何を出し、何を学んだか。
- **マイルストーンごと**:スレッド/ブログ + 本当に新しい価値があるときの Product Hunt ローンチ。

## 逆効果になる失敗

- **成功しか共有しない** — 自慢に見え、信頼はゼロ。泥臭い部分こそ出す。
- **沈黙する** — 1ヶ月の無投稿でフライホイールは死ぬ。強度より頻度。
- **物語のない虚栄の数字** — 「1,000訪問!」は、背後の意思決定がなければ無意味。Build in Publicは**実数を伴うストーリーテリング**であって、数字の羅列ではない。

---

Build in Public は、ローンチの一発勝負ではなく、数ヶ月かけて回す**フライホイール**だ。続けられる1チャネルと、小さな正直な更新から始めてほしい。
